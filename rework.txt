план по переработке ASK-модуля под «Конституцию ботов v3» и твоё уточнение по Refine. После твоего ОК — двигаемся по плану итерациями.

Цели и границы

Не трогаем ENV/Compose, не меняем .env, никакие альтернативные сценарии запуска — строго по правилам.
ASK приводим к антихрупкой архитектуре: тонкие handlers, логика в сервисах, жёсткие инварианты UI/UX, стабильный стейт, идемпотентность, отсутствие «мусорных» сообщений.
UX для Refine — ровно как в tasks2: placeholder первой строки исходного вопроса, одна ForceReply-плашка, без дублей сообщений и без удаления чего-либо. Если короткое уточнение — сервер сам «склеивает» с исходным вопросом.
План работ (5 итераций, каждая с чёткой приёмкой) Итерация 1. Нормализация UX и инвариантов (без крупных перестроек)

Инварианты:
Reply-клава не исчезает никогда; все edit_message_text финального ответа всегда прикладывают панель иконок; после любых действий — явное восстановление main_reply_kb(chat_on).
ForceReply-подсказки не удаляются при успешном/ошибочном LLM — убираем «удалённые сообщения» над вопросом. TTL-чистка только служебных подсказок при явной отмене/удалении.
Источники: «📚» → список (по 5 на страницу) → «Назад» возвращает панель (без «Контекст истёк»); никаких дублирующих ссылок в панели.
Refine UX:
По клику «🔁 Refine»: одна ForceReply «Уточните запрос…» + placeholder = первая строка исходного вопроса (серым в инпуте).
Если юзер ввёл короткую фразу — сервер сам формирует новый prompt как old + "\nУточнение: " + delta; если полный — берём как есть.
Ответ приходит в том же сообщении (редактирование), исходные вопрос/ответ остаются видимыми.
Acceptance:
Нет «удалённое сообщение» над вопросом; «📚 → Назад» без «Контекст истёк»; Refine — один инпут с placeholder, без дублей; reply-клава всегда видна.
Итерация 2. Разделение логики на сервисы (модульность по Конституции)

Выносим из app/handlers/ask.py в сервисы (без Telegram-зависимостей):
services/ask_list.py: поиск/лист/пагинация с subquery-distinct, area = active+linked.
services/ask_selection.py: toggle_selection, автоклир, валидация выборки.
services/ask_answer.py: формирование итогового текста, подсчёт бюджета/стоимости, сбор строки контекста.
services/llm_pipeline.py: вызов модели, ретраи, метаданные; без знания Telegram.
Контракты (узкие и проверяемые):
list_sources(project_ids, term, mode, limit, offset) -> (items, total)
toggle_selection(user_id, source_id) -> added: bool
run_llm(question, source_ids) -> Answer(run_id, text, used_source_ids, meta)
Acceptance:
Handlers «тонкие»: парсят callback, валидируют state, зовут сервисы, рендерят UI. Никаких LLM вызовов в UI-ходах (List/Toggle/Delete/Import).
Итерация 3. Единая схема стейта и идемпотентность

Единый формат last_answer и вспомогательных полей (ask_prompt_msg_id, ask_page_msg_ids, ask_footer_msg_id).
Валидация стейта на входе в каждый handler (дефолты, совместимость, state_version).
Идемпотентность действий (save/pin/summary/delete/refine): повторные клики не ломают, возвращают корректный статус; debounce по run_id/answer_msg_id; короткие замки на пользовательских критичных участках.
Acceptance:
Повторные клики по иконкам не «ломают» панель/контекст; «Нет контекста» не сыпется при нормальном ходе.
Итерация 4. Рендер/безопасность/телеметрия

Единый слой рендера ответов (HTML/MarkdownV2-экранирование), «UTF‑8 Everywhere» + NFC нормализация (уже частично есть).
Контроль «чистоты»: никаких «…»/«точек», все подсказки — toast/всплывашки, редактирование существующих сообщений.
Телеметрия/логи: user_id, chat_id, action/callback, run_id, duration, tokens_in/out (если нужно для cost), ошибок.
Acceptance:
Нет «мусорных» сообщений; логи/метрики покрывают основные действия; ответы безопасны к рендеру.
